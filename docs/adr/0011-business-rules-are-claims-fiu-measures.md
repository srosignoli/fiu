# Business rules are claims Fiu measures, whoever wrote them

A business rule ("orders over €50 ship free", "at most 3 suggestions a day") is a claim about what the system does. Teams keep such claims in their heads, in specs, and in tools that write them down for them, and nothing checks them against the code: a rule can be wrong the day it is written, or turn wrong when the code changes. Fiu already measures behaviour without trusting anyone's word ([ADR 0007](./0007-answers-are-measured-never-asserted.md)), so a rule becomes the topic of a Prediction: a Scenario where the rule makes a difference, whose true answer is what the code does, measured, whatever the rule says. The model that wrote the Prediction says which outcome the rule predicts, and whether the code agrees follows from which outcome the gate measured as true.

Rules come from three sources, and the rest of Fiu treats them alike. The team's own `.fiu-rules.md`, committed with the code: one rule per Markdown list item, a heading as its domain, and an optional `→ path#symbol` pinning where it is enforced. Understand-Anything's domain graph, when there is one ([ADR 0010](./0010-understand-anything-is-read-as-orientation-never-as-links.md)). And a sentence the human types, when it matches no known rule and says enough to be one (4 words or more). A rule shows its source wherever it is shown; the team's file wins over a model-written rule with the same text; turning Understand-Anything off removes only its rules.

Where a rule is enforced is the weak part: a pinned rule needs no guess, a rule naming a function or a constant leads to the code using it, and otherwise Fiu searches the rule's words (among its domain's files, when it has one) and keeps only places sharing several of them. A guess is always confirmed by the human before anything is spent. The rule is never shown before answering, since it often states the answer. A check holds while the function it measured is unchanged; once that changes, the rule is due for a re-check.

The verdict is measured too: the model only says which of the four outcomes the rule predicts, and the code follows the rule when that outcome is the true one. That leaves the model one judgement, matching a sentence to an outcome, which the human sees in the reveal; it is also what lets a cheaper model write rule checks without being trusted with the verdict. A rule's verdict is shown only once its Prediction is answered.

Checking rules after commits is opt-in (`fiu auto on --rules`) and quiet: a commit that changes the function at a rule's known place, pinned by the team or confirmed by a past check, gets a rule check in place of its usual background Workout, under the same consent and caps, with the commit's old behaviour as one of the options. Fiu never turns this into a gate. It never blocks a commit or a push, fails a build, or tells anyone; a developer who doesn't ask for it sees nothing. Background generation may also use its own model (`auto.model`): Verified means the same whichever model wrote a Workout, so a weaker one costs failed attempts, not wrong answers.

We rejected showing a rule's verdict before its Prediction is answered (it would be an alert, and give the answer away), checking rules located only by search after commits (Fiu would act on a guess nobody confirmed), and a CI or pre-push mode that fails on a broken rule (Fiu is practice, not enforcement; teams that want a gate have tests). We also rejected keeping rules as part of the Understand-Anything integration (the measurement never needed it, and most repositories will never have its graph), storing the team's rules in `.fiu/` (Fiu keeps that out of git, and rules are the team's to share and review), extracting rules from documents with a model call of Fiu's own (Understand-Anything already does this, and a team can write the rules that matter in one line each), and treating a rule's agreement as Verified (only the behaviour is measured; whether a sentence describes it is a reading).
