# Workouts for people who don't read code: the answer is always measured, never asserted

Some of the people who need a mental model of a codebase will never open a source file: engineering managers, architects, and developers who let agents write all of their code. They still steer agents, triage incidents, and check behaviour against what was promised, so Fiu serves them with Predictions: a plain-English Scenario and four outcomes to choose from. Each outcome is established by running code in the sandbox. The true one is what the code extracted from the repository does. Each wrong one is what a small Variant of that code does, standing for a plausible misunderstanding. The model writes the Scenario, the Variants, and the tests, but whether an option is true is never the model's word: a Prediction is Verified only when each option's test passes against exactly one version of the code, the true option against the Reference Solution.

We rejected quizzes whose answers can't be measured: multiple-choice questions about ADRs, the spec, or the tech stack, grounded only by citations, and "spot the spec drift" between requirements and summaries the model writes. They would be cheaper to build and closer to what these readers read, but they would be the first Workouts whose correctness rests on the model, and "Verified" would stop meaning one thing. If such quizzes are ever wanted, they will be something other than a Workout. The cost: Predictions are limited to behaviour one self-contained file can reproduce (per [ADR 0001](./0001-workouts-are-stdlib-only.md)), so a workflow that spans several modules is modelled with fakes, and only the Scenario and option texts, not their link to the tests, depend on the model's honesty.

**Extended by Diagnosis (v5.0).** A Diagnosis runs the same idea backwards: from a practice incident to its Cause. The healthy code shows no Symptom, and each Cause's Variant shows only its own, measured by running all five versions. The same limit applies: that the English says what the tests assert is the model's word.

**Extended by What-if (v5.1).** A What-if measures what the code does with a Proposed Change, against today's code anchored to the source file. One more thing rests on the model: that the changed code is what the human's sentence meant. So its reading is always shown before answering, the code change after, and the reveal says the measurement covers one unit, not the whole system.
